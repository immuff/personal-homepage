# Agent 与 RAG（三）：从“RAG 已死”到检索方案选型

每隔一段时间，就能看到“RAG 已死”的讨论：代码可以直接搜索，文档可以整份交给长上下文模型，Agent 还能自己决定查什么。那套“切块、Embedding、向量库、Top-k 召回”的管线，还有必要吗？

我觉得这个问题值得问。但判断一种方案是否还有用，需要先说清楚讨论的是哪一层，再看它要解决的具体任务。

这篇文章由我的 RAG 笔记补充整理而成，技术核对和文字整理由 Codex 辅助完成。文中的选型建议属于工程判断，没有附上我自己的对照实验；引用的研究结论只在其测试条件下成立。网页发布日期为 2026 年 10 月 26 日。

## 一、先说清楚，我们在讨论哪一种 RAG

模型的参数知识存在更新边界，也未必包含企业内部 Wiki、私有代码库和刚刚变化的业务记录。检索可以在回答时提供外部材料，但材料是否新鲜、是否有权限访问、是否足以支持答案，还需要系统保证。

经典 RAG 论文将生成模型与可检索的外部非参数记忆结合，用检索到的材料辅助生成。[1] 在这篇笔记中，我会区分三个层次：

| 层次 | 这里的含义 | 例子 |
| --- | --- | --- |
| 检索增强生成 | 按任务检索外部信息，再让模型据此生成回答 | 搜索制度文件后回答报销问题 |
| 常见的向量 RAG 基线 | 文档解析、切块、向量化、相似度召回、上下文组装、生成 | 在知识库里找若干相关片段 |
| 更广的上下文工程 | 决定每轮模型看到哪些指令、历史、工具结果和外部材料 | 管理任务状态、读取文件、压缩历史 |

`grep`、BM25、向量搜索和 Web 搜索都可以成为 RAG 的检索环节。搜索结果确实被用于生成时，把这条链路称为检索增强生成是合理的；单独执行搜索、读取用户已经给出的全文，则不必都贴上 RAG 标签。

因此，一个 Coding Agent 采用文件导航和按需搜索，只能说明它选择了另一种获取上下文的方式。由此推导“所有 RAG 都过时了”，缺少论据。

**我更关心的问题是：在当前数据、查询和预算下，这套检索管线是否带来了可测量的收益？**

## 二、结构化程度有参考价值，查询形态同样重要

我最初把选型归结为“非结构化数据适合 RAG，结构化数据适合精确搜索”。这个判断过于简化：数据的组织方式会影响工具选择，但用户怎样提问，往往直接决定了检索难点。

### 已知名字时，先利用精确线索

如果已经知道函数名、错误码、订单号或配置键，就应该充分利用这些信息。例如定位 `validate_token` 的定义，符号索引或精确搜索通常是合理起点。

代码还包含路径、模块、导入关系、类型和调用关系。查定义、找引用、分析调用方时，LSP、AST 或代码导航工具可以提供文本相似度以外的结构证据。把代码只当成一堆待切块的自然语言，可能丢掉这些现成的线索。

不过，代码具有语法结构，不代表所有编程问题都是精确查询。

### 不知道实现名称时，存在语义鸿沟

“登录失效后，系统在哪里要求重新认证？”可能涉及 `session`、`refresh_token`、中间件和前端路由守卫。提问者并不知道具体的函数名，也未必知道项目采用了哪套命名。

可考虑的办法包括：

- 扩展查询词，把“鉴权”展开成 `auth`、`login`、`session`、`jwt` 等候选词，再用搜索结果修正方向。
- 先找到入口文件，再沿导入和调用关系读取实现。
- 用向量检索补充自然语言到代码、注释和设计文档之间的语义匹配。

这几种方法可以组合。Anthropic 的 Contextual Retrieval 教程本身就使用代码库演示向量与 BM25 检索。[2] 这足以说明“代码一律不需要向量检索”不是稳妥结论；具体是否值得维护索引，还要看仓库和任务。

### 表格和数据库，要区分定位与计算

对于“上个月各地区的销售额是多少”，适合让 SQL 或计算引擎执行过滤、聚合与排序。只召回几段相似文本，无法保证统计完整性。

但找到正确的数据表、指标定义、字段说明，仍可能需要检索。问数系统可以先查数据字典，再生成受约束的 SQL，最后根据查询结果解释答案。

| 查询类型 | 可优先尝试的工具 | 需要注意的问题 |
| --- | --- | --- |
| 已知标识符、路径、错误码 | 精确搜索、符号索引 | 同名对象和版本差异 |
| 关键词明确，希望按相关性排序 | BM25 等全文检索 | 分词、别名与词汇不匹配 |
| 自然语言描述，叫法差异较大 | 向量检索或混合检索 | 相似内容未必支持当前问题 |
| 精确过滤、排序、聚合、关联 | SQL、结构化查询引擎 | 字段口径、权限与计算正确性 |
| 需要沿线索不断深入 | Agent 驱动的搜索和阅读 | 轮次、停止条件与累积错误 |

## 三、长上下文能替代多少检索

对于一份短合同或少量相关文件，直接读取全文很有吸引力：少了切块和召回环节，也更容易保留定义、条款和附件之间的关系。

但要把三个判断分开：**内容放得下、模型有效利用了内容、答案覆盖了任务要求**。它们并不等价。

《Lost in the Middle》在其测试模型和任务上发现，相关信息在上下文中的位置会影响表现。[3] 这提醒我检查长上下文的有效利用率，不能据此断言所有当前模型都会以相同程度退化，也不能推导“Top-k 检索必然更准”。

EMNLP 2024 的一项对照研究，在所测试的模型和数据集上观察到：资源充足时，长上下文方案的平均表现更好，RAG 则具有成本优势；研究还探索了两者之间的路由。[4] 这是特定实验的结果，不能直接当成所有业务的排名。

我的选型思路是：

| 条件 | 值得先验证的方案 |
| --- | --- |
| 少量文件、可完整容纳、需要逐条对照 | 全文输入，加检查清单和明确引用 |
| 大量材料、每次只问局部事实 | 先检索，再读取相关段落及必要上下文 |
| 问题要求跨文档比较 | 先确定比较范围，再按文档或章节组织材料 |
| 要求全库覆盖、穷尽列举或准确统计 | 显式遍历或查询，记录覆盖范围，分批处理后核验 |

还要算完整账：长上下文的费用受模型定价、缓存命中和材料复用影响；RAG 则有解析、索引、增量更新、查询和重排成本。文档变化后需要处理受影响的索引，不能理解成“建索引时处理一次，以后就没有成本”。

**长上下文减少了某些场景的检索需求，也能与检索配合：先筛出相关文件，再用较长上下文完整阅读。**

## 四、Top-k 的局限，能说明 RAG 做不了全局推理吗

普通片段召回更容易回答“某件事在哪里写过”。面对“所有合同都有哪些共同风险”或“整个代码库有没有遗漏鉴权的入口”，仅凭相似度最高的几个片段，证据覆盖往往不够。

这里的限制主要来自检索和覆盖策略。模型可以基于多段证据推理，但如果相关材料没有进入上下文，它就缺少必要依据。一次局部检索，也不能证明全库不存在其他情况。

应对办法可以是章节级检索、父子块回填、逐步补检索、分层摘要、显式遍历，或针对关系和全局主题组织索引。GraphRAG 的官方设计就包含基于社区摘要的 Global Search。[5] 这说明检索增强也能围绕全局问题设计；额外索引和摘要同时会引入成本与信息损失，不能保证穷尽或自动正确。

例如检查“所有 API 是否都有鉴权”，我会要求系统先确定 API 清单，再逐项检查并记录结果，最后列出未覆盖和无法判断的部分。只给它一句“多检索几次”，不足以证明检查完整。

## 五、Agentic RAG 与 Embedding，解决的是不同层的问题

Embedding 是表示和匹配信息的一种方式；Agentic RAG 则涉及由模型决定检索计划、调用工具、检查证据和继续查找。Agent 可以调用关键词搜索，也可以调用向量检索，两者没有排他关系。

Anthropic 的上下文工程文章介绍了按需加载材料的策略，也描述了 Claude Code 结合预先提供的上下文与 `glob`、`grep` 等导航工具的方式。[6] 这是一个具体的工程案例，并不能替所有代码库作选型。

模型重写查询，确实可能缓解词汇不匹配。例如把“登录续期”转换成 `refresh token`、`session renewal` 等候选词。但改写依赖模型对领域和项目的理解：它可能漏掉内部术语，也可能扩展出错误方向。

所以，“Agentic + BM25 能否替代向量检索”应该变成一个对照实验：同一批问题、同一个语料版本、相近的预算，比较证据召回和最终答案。

我会先验证单轮检索是否足够，再决定是否引入循环。若采用 Agentic 检索，需要明确：

1. 每轮查什么、结果最多返回多少。
2. 哪些证据还缺失，下一次调用能补什么。
3. 最大轮数、时间和费用预算。
4. 什么时候停止，证据不足时怎样说明。

多轮调用会增加一些任务的开销，也可能通过有针对性的搜索减少无关输入。没有实测时，不能给出统一的“多耗 2–5 倍 token”结论。

## 六、把“最佳实践”改成有条件的决策

我保留“从轻量方案开始”的原则，但不会把它写成 `grep → BM25 → Embedding → Agentic` 的固定升级路线。它们有不同的适用条件，复杂度也不等于效果。

| 原先的简化判断 | 更稳妥的做法 |
| --- | --- |
| 默认先用 grep | 本地代码、关键词明确时先试精确搜索；数据库统计先用查询引擎 |
| 量级大了再加 BM25 | 需要全文相关性排序、搜索体验或复杂查询时就可以评估倒排索引 |
| 只有同义词问题才用 Embedding | 把概念描述、跨语言和自然语言到代码等语义需求纳入评测 |
| 模型够强就上 Agentic | 只有任务确实需要计划、补查和迭代时，才承担循环的额外成本 |
| 文件级一定优于 Chunk 级 | 小文件可整体读取；大文件按章节或函数定位，再补必要上下文 |
| 只有 metadata join 才需要数据库 | 权限、过滤、版本、并发和一致性都可能影响存储选型；有元数据也不必立即换基础设施 |

还有一个容易混淆的点：[BM25](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity) 是词项相关性评分方法，通常配合倒排索引；[HNSW](https://arxiv.org/abs/1603.09320) 是近似最近邻索引方法，可用于向量搜索。它们不处于同一抽象层。对延迟的判断应覆盖完整链路，包括存储读取、过滤、重排和模型生成。

## 七、八个场景，把判断落到具体问题

下面是我的起步方案，实际效果仍需要用任务数据验证。

### 1. 中小代码库里定位函数、修改代码，用什么

先查看目录和项目说明，使用文件匹配、精确搜索和符号导航定位候选位置，再读取实现、调用方与测试。只有当概念描述经常无法映射到代码时，再比较查询扩展或向量检索的收益。

搜索结果适合帮助定位；修改前仍要阅读足够上下文，修改后通过相关测试和运行结果验证。

### 2. 代码库很大，grep 扫盘太慢怎么办

先确认搜索范围：能否限定仓库、模块、文件类型，排除构建产物和依赖目录？若扫描仍成为瓶颈，再评估全文索引、符号索引及增量更新。

扫描慢本身无法证明向量库就是下一步，还要确认任务需要怎样的匹配能力。

### 3. 鉴权相关代码分散在 auth、login、session、jwt 中，搜不全怎么办

先扩展候选词，找到入口后沿调用和导入关系检查。若自然语言到实现的映射仍然困难，可以增加语义检索，与精确搜索的结果合并。

要区分“找到一些相关代码”和“覆盖所有鉴权路径”。后者需要入口清单、检查记录，以及明确列出的盲区。

### 4. 分析一份合同，或对比两份文件，是否需要 RAG

材料能完整容纳时，可以先试全文输入。按定义、义务、付款、违约、终止和附件等维度逐项对照，并给出条款编号或页码。

材料太长时，可先按章节对齐、分批比较，再汇总核验。仅检索相似度最高的几个段落，不能支撑“已经找出全部差异”的承诺。

### 5. 几十万份法律、客服或 Wiki 文档，怎样做问答

可以从全文与向量的混合检索基线开始，比较是否需要重排、章节上下文回填和查询改写。文档解析、去重、版本与更新流程，需要与检索一起设计。

每个证据片段最好保留文档标识、章节或页码和更新时间，让读者能够回到原文核对。无答案问题也应进入测试集。

### 6. 企业数据达到 TB/PB 级，长上下文装不下怎么办

先按数据类型选执行层：结构化数据交给数据库或分析引擎，文档和日志进入合适的搜索系统，模型只读取与当前任务有关的结果。

原始字节规模不能直接决定向量数量，也不意味着全部数据都应该向量化。数据分区、查询过滤、计算下推和权限隔离，都要在模型读取前处理。

### 7. 要按作者过滤、按提交时间排序、按路径匹配怎么办

把作者、时间、路径建成明确字段，用支持这些条件的查询系统执行。语义相关性与时间顺序是不同排序目标，应明确谁优先，必要时采用两阶段检索。

权限条件应由可信系统约束，在检索和上下文组装中保证只使用授权材料。若只能在候选召回后过滤，需要评估召回损失；不能先把越权材料交给模型，再要求它忽略。

### 8. 模型和预算都充足，怎样追求更好的检索质量

先建立高质量测试集，再比较混合召回、重排、查询分解和 Agentic 补检索。质量没有脱离任务的统一最优解：有些问题受益于多轮探索，有些更适合确定性的查询或完整阅读。

可以同时给 Agent 精确搜索、结构化查询和语义检索工具，但工具描述要说清适用条件；系统还需要限制预算、记录证据，并验证它是否选对了工具。

## 八、如何验证这套选择是否真的有效

我会把评测分为“检索到了什么”和“最后回答得怎样”两部分，避免看到错误答案就直接更换 Embedding 模型。

| 层次 | 要检查的内容 | 能帮助定位的问题 |
| --- | --- | --- |
| 解析与入库 | 原文、表格、标题、页码是否保留正确 | 证据从一开始就没有进入系统 |
| 召回 | 所需证据是否出现在候选集，组合证据是否齐全 | 查询、过滤或召回策略有遗漏 |
| 重排与上下文组装 | 必要证据是否被截断、挤出或拆散 | 候选已找到，模型却没有看到 |
| 答案 | 事实是否正确，引用是否支持结论 | 模型误读、推理错误或无依据补全 |
| 无答案与覆盖 | 应拒答时是否拒答，穷尽任务是否完成检查 | 把局部命中误当成完整结论 |
| 运行成本 | 端到端延迟、尾延迟、模型费用、索引维护成本 | 质量改善能否满足生产约束 |

测试问题应包括精确查询、同义改写、多跳组合、全局比较、时效与版本冲突、无答案以及权限边界。对照时固定语料快照、模型和评测口径，并记录各方案实际消耗的预算。Recall@k 适合观察召回，但多证据任务还要检查证据集合是否完整。

外部材料还可能包含错误内容或提示注入。检索到的文本应作为待核对的证据，不能因此获得修改系统规则或调用高权限工具的资格。这些边界要靠权限和执行层约束，不能只靠提示词提醒。

## 九、我目前的判断

我仍然倾向于先做能验证的轻量基线，再针对真实失败增加复杂度。

已知名字，就利用精确线索；需要统计，就让查询引擎计算；存在词汇与概念差异，就比较语义和混合检索；需要全局对照，就明确材料范围与覆盖方式；需要边查边判断，再引入有预算和停止条件的 Agent 循环。

**Embedding、长上下文和 Agentic 检索都是可选的工程手段。选择它们的依据，应当是任务上的证据覆盖、答案质量、延迟、成本与维护负担。**
