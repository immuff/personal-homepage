# Agent 与 RAG（一）：从提示词工程开始

这是「Agent 与 RAG」系列的第一篇。我想先从提示词工程开始，把任务、上下文、检索和工具调用之间的关系慢慢理清。[查看本系列文章](/blog?q=Agent%20%E4%B8%8E%20RAG)。

提示词工程在培训中经常是一个很大的知识模块，但在我接触到的面试问题里，很少作为一个独立模块出现。比起记住多少种提示词技巧，我更关心的是：怎样把任务交代清楚，又怎样判断模型的回答是否真的可用？

这篇笔记参考了原稿中记录的[课程梳理视频](https://www.youtube.com/watch?v=p09yRj47kNM)，部分框架梳理和示例由 Codex 辅助整理。下面先保留一个容易使用的框架，再把它放回项目和面试问题中理解。

## 先把任务写清楚：TCREI

TCREI 可以把提示词的设计和改进串成五步：

| 步骤 | 含义 | 写提示词时要回答的问题 |
| --- | --- | --- |
| T：Task | 任务 | 要 AI 完成什么？需要什么输出格式？ |
| C：Context | 背景 | 为谁做？用于什么场景？有哪些条件？ |
| R：References | 参考 | 有哪些资料、示例或风格样本？ |
| E：Evaluate | 评估 | 结果是否准确、相关，是否符合要求？ |
| I：Iterate | 迭代 | 哪个地方没达到要求？下一轮具体改什么？ |

**前三项用于组织输入，后两项用于检查和改进结果。** 因而，写完一段提示词只是开始，还需要拿到输出、检查差距，再决定下一轮怎么改。

任务中还可以指定角色和格式。例如：“从技术面试官角度审阅，以表格输出问题与修改建议。”角色帮助限定视角，格式帮助限定交付物。Google 的[提示设计资料](https://cloud.google.com/vertex-ai/generative-ai/docs/learn/prompts/prompt-design-strategies)同样强调明确指令、上下文、示例，以及持续测试和迭代。

放到知识库问答里，上下文也不只是手工粘贴的一段文字。RAG 可以先从外部资料中检索相关内容，再把这些内容提供给模型，辅助它生成回答。提示词则需要说明：资料是什么、如何使用资料、证据不足时怎么办。[RAG 官方概述](https://cloud.google.com/vertex-ai/generative-ai/docs/rag-engine/rag-overview)

## 回答不理想时，给出能执行的反馈

期待一次得到满意答案，往往会忽略任务中尚未说清楚的部分。原稿整理了四种迭代方法：

| 方法 | 怎么改 |
| --- | --- |
| 回到框架补缺项 | 补充遗漏的背景、角色或参考示例 |
| 拆短、拆步骤 | 将一大段混合要求拆成清楚的小任务 |
| 换一种表述或相似任务 | 换个角度描述目标，尝试另一种表达或类比 |
| 增加约束 | 明确范围、数量、风格、预算或禁止事项 |

反馈要能执行。“再专业一点”很模糊；“删掉空泛评价，补上技术选择、验证方法和局限”更容易检查。后一种反馈同时告诉模型改哪里，也告诉自己下一轮应该检查什么。

## 多模态输入，也要交代资料的用途

同一个框架也可以用于图片、音频等输入，以及邮件、数据分析和演示文稿任务。实际使用时，除了添加附件，还要说清楚它在任务中的作用：

- “这张图用于参考配色，构图请重新设计。”
- “这份表格是计算依据，请先核对字段和指标口径。”
- “这篇文章只参考表达风格，其中的数据不能沿用。”

这三个例子是 Codex 辅助补充的示例。参考资料的作用越明确，越容易评估 AI 是否正确使用了它；输出里的事实、计算和引用仍然需要人工核对。

## 从提示链到角色模拟，先分清各自的作用

除了基本框架，笔记里还记录了几种进阶技巧。先用简短的方式理解它们：

| 技巧 | 笔记中的理解 |
| --- | --- |
| 提示链 Prompt Chaining | 把前一步的输出交给下一步，逐步完成任务 |
| 思维链 CoT | 通过分步推理组织解题；对外的分步解释仍需独立核验 |
| 思维树 ToT | 探索不同候选路径，再比较、筛选和深化 |
| 元提示 Meta Prompting | 让 AI 帮助设计或改进提示词 |

分步骤解释仍然需要核验。我的做法是要求**关键依据、必要的计算过程和验证方法**，不能因为解释流畅就接受结论，也不能把生成的解释当作模型内部推理过程的完整记录。

模拟练习和专家反馈还可以通过对话角色来组织。设计时需要交代角色、场景、互动规则、结束口令，以及结束后的反馈方式。例如，模拟面试不能只写“你是面试官”，还要说明问什么、怎样推进、何时结束，以及最后如何评价。

这里也需要区分两种“Agent”：角色模拟主要规定对话中的身份和互动方式；工程中的 Agent 则还涉及模型如何选择行动、调用工具，并根据环境反馈继续执行。仅写一句角色设定，还不足以实现这些能力。Anthropic 的[Agent 工程文章](https://www.anthropic.com/engineering/building-effective-agents)也把工具、环境反馈和执行循环作为理解 Agent 的重要部分。

## 一份可以复用的提示词模板

把前面的内容收在一起，可以先用下面这份模板组织请求，再按具体任务删改：

```text
任务：
请帮我完成【具体任务】。

背景：
我目前处于【阶段】，结果将用于【场景/受众】。
已有条件是【……】，主要限制是【……】。

参考资料：
【粘贴内容或添加附件】
这些资料分别用于【事实依据/风格参考/格式示例】。

输出要求：
请按【格式】输出，包含【必要内容】。
范围控制在【……】。

验收标准：
结果需要满足【可检查的标准】。
请明确区分事实、推测和待验证信息。

信息缺失时：
影响结论的缺失信息请先指出；
其他部分可以说明假设后继续。
```

模板的作用是提醒自己交代任务。具体任务不需要的字段可以删去，能够帮助模型判断的事实、限制和验收条件则应保留。

## 面试里，怎样回答“如何提升任务稳定性与准确性”

如果面试官问：“如何设计 Prompt 来提升任务稳定性与准确性？”我会从下面几个方面组织回答。

首先，需要明确任务目标、输入含义、执行规则、边界条件和输出格式，尽量减少模型自行猜测。例如，分类任务要明确标签集合、每个标签的判定标准，以及信息不足或标签冲突时如何处理。

其次，为模型提供与任务相关且可信的上下文。事实性任务可以结合 RAG、数据库或工具查询，并要求模型根据提供的证据回答。证据不足时，应明确返回不确定或请求补充信息，而不是自行编造。对于规则复杂或容易混淆的任务，可以提供少量 Few-shot 示例，尤其覆盖正常情况、边界情况和反例。

当任务容易被清楚地拆成若干子任务时，可以把理解、检索、决策和执行分开。例如：

```text
意图识别 → 信息检索 → 生成候选结果 → 结果校验 → 输出或重试
```

每一步都应有明确的输入和输出。不过，这是一种可选的组织方式，不是所有任务都必须经过完整流程。是否拆分，需要结合实际效果、调用成本和延迟判断。[提示链的适用条件](https://www.anthropic.com/engineering/building-effective-agents)

下游程序需要使用结果时，应优先采用接口支持的结构化输出，例如用 JSON Schema 约束字段类型和枚举值；需要调用工具时，使用工具调用机制传递结构化参数。**结构符合要求，并不等于事实和业务语义正确。** 模型输出进入程序时，仍要在这个边界检查必要的字段、类型、业务规则和权限。[结构化输出说明](https://ai.google.dev/gemini-api/docs/structured-output)

最后，要通过测评而不是主观感觉判断 Prompt 是否有效。可以建立包含正常、边界和历史失败样本的测试集，将 Prompt、模型版本和参数一起版本化，通过任务成功率、事实准确率、格式合法率、工具调用正确率等指标进行回归测试。

需要注意的是，Prompt 只能降低模型行为的不确定性，不能提供绝对保证。事实核验、工具权限、API 重试、业务规则和高风险操作确认，仍需要由程序和系统机制完成。
